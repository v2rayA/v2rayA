# Прозрачный прокси

При включённом прозрачном прокси трафик поступает в ядро без настройки приложений; какой трафик поступает в ядро, зависит от реализации. Параметр **Настройки → Прозрачный прокси/системный прокси** включает его и задаёт режим разделения трафика; параметр ниже выбирает реализацию.

## Режимы

| Режим                                                     | Трафик через прокси                                                                                                                                                                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Не разделять трафик                                       | весь                                                                                                                                                                                                         |
| Прокси для сайтов, кроме сайтов материкового Китая        | весь, кроме китайских доменов и адресов (`geosite:cn`, `geoip:cn`) и частных адресов; сайты за пределами Китая, Google и адреса Гонконга и Макао идут через прокси, даже если подходят под китайское правило |
| Прокси только для GFWList                                 | домены из GFWList (`gfw` и `greatfire` из файла Loyalsoldier) и диапазоны адресов Telegram; сначала нажмите **Обновить GFWList**, без этого файла включить режим нельзя                                      |
| Режим разделения трафика совпадает с режимом порта правил | режим порта правил, включая RoutingA                                                                                                                                                                         |

## Реализации

| Реализация       | Платформы                                                     | Примечания                                                                                                                            |
| ---------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `redirect`       | Linux                                                         | iptables/nftables `REDIRECT`; только TCP, а также DNS на порту 53, перенаправляемый в DNS-модуль ядра (порт 52353) в режиме «служба и перехват» |
| `tproxy`         | Linux                                                         | iptables/nftables `TPROXY`; TCP и UDP                                                                                                 |
| `tun`            | Linux, Windows, macOS                                         | ядро открывает устройство TUN; TCP и UDP; само исключает v2rayA и ядро                                                                |
| Системный прокси | Windows; Linux и macOS при работе не от имени root (`--lite`) | задаёт настройки прокси в среде рабочего стола (GNOME и KDE в Linux); действует только на приложения, которые учитывают эти настройки |

Для `redirect` и `tproxy` нужны права root и `iptables` или `nftables`; для `tun` нужны `/dev/net/tun` и `ip` в Linux, а в Windows и macOS — права администратора.

Параметр **Префиксы исключаемых интерфейсов** исключает из `redirect` и `tproxy` трафик, поступающий через указанные интерфейсы (мосты Docker, туннели VPN; по умолчанию `docker*`, `veth*`, `wg*`, `ppp*`); их DNS по-прежнему перехватывается в режиме «служба и перехват».

`--redirect-respect-bound-device` (Linux) выводит из-под `redirect` TCP-соединения, привязанные к интерфейсу через `SO_BINDTODEVICE`: проверки подключения NetworkManager — именно такие соединения, и после перенаправления они сообщают об ограниченном подключении, а зависящие от них приложения остаются офлайн. По умолчанию выключено. Когда включено, служба помечает такие сокеты меткой `0x80` через cgroup BPF; для этого нужны ядро 5.14 или новее и cgroup v2, без них `redirect` не запускается.

## TUN

Ядро создаёт устройство TUN и назначает ему адрес. Если включён параметр **Автоматическая маршрутизация**, v2rayA устанавливает маршруты, а в режиме «служба и перехват» направляет системный DNS-резолвер к ядру; если выключен, это делают скрипты настройки и очистки из раздела **Настроить скрипт маршрутизации**.

В TUN никогда не попадают собственные соединения ядра, исходящее подключение `direct` и запросы DNS-модуля к вышестоящим серверам (в Linux — за счёт метки сокета, в Windows и macOS — привязки к физическому интерфейсу). v2rayA и ядро исключаются всегда; параметр **Процессы, исключаемые из TUN** позволяет исключить другие процессы по именам исполняемых файлов; указывайте по одному имени в строке, для соединений, у которых можно определить процесс-владелец; в режиме «служба и перехват» их DNS по-прежнему поступает в DNS-модуль ядра. Маршруты, более специфичные, чем маршрут по умолчанию (подключённые сети, статические маршруты), также обходят TUN.

В режиме «служба и перехват» на незашифрованные DNS-запросы к порту 53, попавшие в TUN, отвечает DNS-модуль ядра согласно правилам DNS; зашифрованный DNS не перехватывается. В этом случае в Windows системный DNS-резолвер направляется к шлюзу TUN, в macOS — к DNS-модулю ядра, принимающему запросы на `127.0.0.1`; для этого порт 53 должен быть свободен.

В двух других режимах TUN такого посредника не создаёт и системный резолвер на обеих платформах не меняется; дошедший всё же запрос выходит с устройства напрямую. То же верно при выключенной **Автоматической маршрутизации**, когда сеть настраивает скрипт: v2rayA не меняет настройки резолвера, поэтому DNS остаётся в ведении скрипта.

Известное ограничение: в Windows и macOS приложение, напрямую запрашивающее DNS-сервер локальной сети, по-прежнему обходит TUN.

## DNS

Раздел **Настройки → Настройки DNS** содержит режим DNS и правила DNS-модуля ядра.

| Режим                 | DNS-модуль | Системные запросы                                                              |
| --------------------- | ---------- | ------------------------------------------------------------------------------ |
| Выключен              | не запущен | не изменяются                                                                   |
| Только служба         | запущен    | не изменяются: резолверы, DNS-правила брандмауэра и посредник TUN остаются как есть |
| Служба и перехват     | запущен    | направляются к нему: резолвер перенастраивается, порт 53 перенаправляется       |

Режим отвечает сразу на два вопроса, которые раньше смешивались: работает ли модуль и направляются ли к нему системные запросы, — и режим «только служба» отвечает на них по-разному. Режимы «выключен» и «только служба» одинаково пропускают обычный TCP/UDP на порту 53 через `redirect`, `tproxy` и системный прокси и отправляют его напрямую из `tun`; зашифрованный DNS и так не направляется в модуль, поэтому отказываться от перехвата ради него не нужно. Выбирайте «только служба», когда DNS уже направлен к v2rayA другой программой, и «выключен», когда DNS не должен отвечать за вас вовсе.

Правила задают, какой вышестоящий сервер отвечает за какие домены и отправляется ли запрос напрямую. По умолчанию запросы для внутренних доменных имён направляются на `127.0.0.1:53` (`localhost`, где должен слушать DNS-резолвер), `geosite:cn` — напрямую на `223.5.5.5`, а всё остальное — через прокси на `1.0.0.1`. Исходящее подключение `direct` отправляет запрос напрямую; любое другое значение направляет запрос через локальный входящий порт SOCKS, поэтому он маршрутизируется как трафик SOCKS. Правило с пустым списком доменов отвечает за все домены, не указанные ни в одном другом правиле. Вышестоящий сервер задаётся адресом (`8.8.8.8`, `dns.google`), `tcp://host`, `tls://host` для DNS over TLS или `https://host/dns-query` для DNS over HTTPS; DNS over QUIC не поддерживается и отклоняется при сохранении.

Режим «выключен» скрывает правила и сохраняет их: их всё равно никто не читает, а удаление означало бы, что после включения режима настроится другая конфигурация.

Сохранение пишет правила и режим двумя запросами, и окно сообщает, какой из них приняла служба. Отказ после записи правил называется именно таким, поэтому повтор отправляет только недостающее.


**DNS для разрешения имён узлов**, рядом с настройками DNS, выбирает общий резолвер имён серверов прокси-узлов. Он применяется к новым подключениям и тестам задержки TCP/HTTP в режимах «Только служба» и «Служба и перехват» независимо от перехвата. В режиме «Выключен» модуль отключён, а узлы используют прежний путь системного разрешения имён. В этом режиме список DNS для узлов и кнопка обновления отключены, но выбор сохраняется; после сохранения включённого режима они снова доступны. Узлам с IP-адресом DNS не нужен. Имена сайтов, серверов подписок и начальное разрешение адресов DNS-серверов используют прежние механизмы.

В этих включённых режимах подключения к узлам и тесты задержки TCP/HTTP ждут готовности встроенного модуля DNS, затем обращаются к его локальному адресу. Модуль напрямую запрашивает выбранный сервер или возвращает ответ из кэша; системный резолвер для имён узлов не используется. Тайм-аут запуска, отмена или завершение ядра прекращают запрос. Ошибка сервера отображается как ошибка DNS-запроса без перехода к другому резолверу. Если ядро остановлено, тесты задержки запускают временное ядро с выбранной конфигурацией DNS и останавливают его после теста.

Список содержит UDP, TCP, DoT и DoH с IP-адресом из правил DNS, исходной системной конфигурации и встроенного резервного списка. В Linux системные DNS читаются из `/etc/resolv.conf`, а при перехвате DNS — из исходной резервной копии. Категории обозначают источник: **группа прямого подключения**, **локальный DNS**, **группа прокси**, **резервный DNS**. Запросы DNS для узлов всегда идут напрямую, даже при выборе источника из группы прокси. Сертификаты DoT/DoH проверяются. Наличие варианта означает допустимый текущий источник, а не проверенную доступность по сети.

Режим **автоматически** после удаления дубликатов выбирает первый адрес первой непустой группы в порядке прямое подключение → локальный DNS → резервный DNS. Как и для явно выбранного адреса, показывается полный URL с протоколом и портом, например `udp://223.5.5.5:53 (автоматически)`. Сбой запроса возвращает ошибку DNS без переключения на другой адрес. Обновление списка и сохранение настроек или правил DNS перечитывают источники. Исчезнувший сохранённый источник остаётся в форме с предупреждением; изменения, делающие его недопустимым, отклоняются. Сначала выберите другой адрес или автоматический режим. Кэш и предзагрузка DNS сохраняются; новые результаты влияют на будущие подключения, существующие сохраняют текущий IP.

## Общий доступ в локальной сети

Параметр **Общий доступ к портам** заставляет входящие порты SOCKS, HTTP и пользовательские входящие порты слушать на всех интерфейсах вместо `127.0.0.1`, чтобы другие устройства могли использовать этот компьютер как прокси; порт API остаётся на петлевом интерфейсе. Чтобы их трафик также проходил через прозрачный прокси, используйте `redirect`, `tproxy` или `tun`, включите **IP-форвардинг**, исключите интерфейс, через который поступает их трафик, из списка исключаемых префиксов и укажите этот компьютер как их шлюз по умолчанию; режимы системного прокси этого не позволяют.
