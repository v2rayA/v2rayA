# پروکسی شفاف

با روشن بودن پروکسی شفاف، ترافیک بدون هیچ تنظیمی در برنامه‌ها به هسته می‌رسد؛ دامنهٔ پوشش به پیاده‌سازی بستگی دارد. **تنظیمات → پروکسی شفاف/پروکسی سیستم** آن را روشن می‌کند و سیاست تفکیک ترافیک را تعیین می‌کند؛ تنظیم زیر آن، پیاده‌سازی را مشخص می‌کند.

## سیاست‌ها

| سیاست                | ترافیکی که از پروکسی می‌گذرد                                                                                                                                                                                        |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| عدم تفکیک ترافیک          | همه‌چیز                                                                                                                                                                                                       |
| پروکسی به‌جز سایت‌های CN | همه‌چیز به‌جز دامنه‌ها و نشانی‌های چینی (`geosite:cn`، `geoip:cn`) و نشانی‌های خصوصی؛ سایت‌های خارج از چین، Google و نشانی‌های هنگ‌کنگ و ماکائو حتی در صورت تطبیق با قانون چینی نیز از پروکسی می‌گذرند |
| پروکسی فقط برای GFWList    | دامنه‌های GFWList (`gfw` و `greatfire` از فایل Loyalsoldier) و محدوده‌های نشانی Telegram؛ ابتدا **به‌روزرسانی GFWList** را اجرا کنید؛ بدون این فایل، این حالت پذیرفته نمی‌شود                                    |
| حالت تفکیک ترافیک مانند پورت قوانین است | حالت پورت قوانین، از جمله RoutingA                                                                                                                                                                         |

## پیاده‌سازی‌ها

| پیاده‌سازی | سکوها                                                    | توضیحات                                                                                                        |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `redirect`     | Linux                                                        | `REDIRECT` در iptables/nftables؛ فقط TCP، به‌علاوهٔ هدایت DNS پورت 53 به ماژول DNS هسته (پورت 52353) |
| `tproxy`       | Linux                                                        | `TPROXY` در iptables/nftables؛ TCP و UDP                                                                      |
| `tun`          | Linux، Windows، macOS                                        | هسته یک دستگاه TUN باز می‌کند؛ TCP و UDP؛ v2rayA و هسته را خودکار مستثنا می‌کند                             |
| پروکسی سیستم   | Windows؛ Linux و macOS در صورت اجرا نشدن با کاربر root (`--lite`) | تنظیمات پروکسی محیط دسکتاپ را اعمال می‌کند (GNOME و KDE در Linux)؛ فقط برنامه‌هایی را پوشش می‌دهد که از این تنظیمات پیروی می‌کنند   |

`redirect` و `tproxy` به دسترسی root و `iptables` یا `nftables` نیاز دارند؛ `tun` در Linux به `/dev/net/tun` و `ip` و در Windows و macOS به دسترسی مدیر نیاز دارد.

گزینهٔ **پیشوندهای رابط‌های مستثنا** ترافیک دریافتی از رابط‌های مشخص‌شده را از `redirect` و `tproxy` مستثنا می‌کند (پل‌های Docker، تونل‌های VPN؛ به‌طور پیش‌فرض `docker*`، `veth*`، `wg*`، `ppp*`)؛ DNS آن‌ها همچنان رهگیری می‌شود.

## TUN

هسته دستگاه TUN را می‌سازد و نشانی آن را اختصاص می‌دهد. با روشن بودن **مسیریابی خودکار**، v2rayA مسیرها را نصب می‌کند و حل‌کنندهٔ نام سیستم را به هسته هدایت می‌کند؛ با خاموش بودن آن، اسکریپت‌های راه‌اندازی و جمع‌آوری در **پیکربندی اسکریپت مسیریابی** این کار را انجام می‌دهند.

مواردی که هرگز وارد TUN نمی‌شوند: اتصال‌های خود هسته، خروجی `direct` و پرس‌وجوهای بالادستی ماژول DNS (با علامت‌گذاری سوکت در Linux و اتصال به رابط فیزیکی در Windows و macOS). v2rayA و هسته همیشه مستثنا هستند؛ گزینهٔ **فرایندهای مستثنا از TUN** فرایندهای بیشتری را بر اساس نام فایل اجرایی، هر نام در یک خط، مستثنا می‌کند؛ این کار برای اتصال‌هایی انجام می‌شود که فرایند مالکشان قابل شناسایی باشد؛ DNS آن‌ها همچنان به ماژول DNS هسته می‌رود. مسیرهای خاص‌تر از مسیر پیش‌فرض (شبکه‌های متصل، مسیرهای ایستا) نیز از TUN عبور نمی‌کنند.

DNS رمزنگاری‌نشده روی پورت 53 که به TUN می‌رسد، طبق قوانین DNS توسط ماژول DNS هسته پاسخ داده می‌شود؛ DNS رمزنگاری‌شده رهگیری نمی‌شود. در Windows، حل‌کنندهٔ نام سیستم به دروازهٔ TUN هدایت می‌شود؛ در macOS به شنوندهٔ هسته روی `127.0.0.1` که به آزاد بودن پورت 53 نیاز دارد.

محدودیت شناخته‌شده: در Windows و macOS، برنامه‌ای که مستقیماً از حل‌کنندهٔ نام شبکهٔ محلی پرس‌وجو می‌کند، همچنان از TUN عبور نمی‌کند.

## DNS

**تنظیمات → تنظیمات DNS** شامل قوانینی است که ماژول DNS هسته از آن‌ها پیروی می‌کند: کدام سرور بالادستی به کدام دامنه‌ها پاسخ دهد و آیا پرس‌وجو مستقیم ارسال شود. تنظیمات پیش‌فرض نام‌های خصوصی را به `127.0.0.1:53` می‌فرستند (`localhost` که به حل‌کنندهٔ نامی نیاز دارد که در آن نشانی گوش دهد)، `geosite:cn` را مستقیم به `223.5.5.5` و بقیه را از طریق پروکسی به `1.0.0.1` می‌فرستند. خروجی `direct` پرس‌وجو را مستقیم ارسال می‌کند؛ هر مقدار دیگری پرس‌وجو را از ورودی محلی SOCKS می‌فرستد تا مانند ترافیک SOCKS مسیریابی شود. قانونی با فهرست دامنهٔ خالی، پاسخ‌گوی هر دامنه‌ای است که در قوانین دیگر نیامده باشد. سرور بالادستی می‌تواند یک نشانی (`8.8.8.8`، `dns.google`)، `tcp://host`، `tls://host` برای DNS روی TLS یا `https://host/dns-query` برای DNS روی HTTPS باشد؛ DNS روی QUIC پشتیبانی نمی‌شود و هنگام ذخیره پذیرفته نمی‌شود.

## اشتراک‌گذاری در شبکهٔ محلی

گزینهٔ **اشتراک‌گذاری پورت** باعث می‌شود ورودی‌های SOCKS، HTTP و ورودی‌های سفارشی به‌جای `127.0.0.1` روی همهٔ رابط‌ها گوش دهند تا دستگاه‌های دیگر بتوانند از این دستگاه به‌عنوان پروکسی استفاده کنند؛ پورت API روی رابط loopback می‌ماند. برای عبور ترافیک آن‌ها از پروکسی شفاف نیز، از `redirect`، `tproxy` یا `tun` استفاده کنید، **هدایت IP** را روشن کنید، رابط دریافت ترافیک آن‌ها را از پیشوندهای مستثنا خارج نگه دارید و دروازهٔ پیش‌فرض آن‌ها را روی این دستگاه تنظیم کنید؛ حالت‌های پروکسی سیستم این کار را انجام نمی‌دهند.
