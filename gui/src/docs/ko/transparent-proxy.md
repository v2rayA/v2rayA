# 투명 프록시

투명 프록시를 켜면 애플리케이션에서 별도로 설정하지 않아도 트래픽이 코어에 도달합니다. 적용 범위는 구현 방식에 따라 다릅니다. **설정 → 투명 프록시/시스템 프록시**에서 켜고 트래픽 분할 정책을 선택합니다. 그 아래 설정에서 구현 방식을 선택합니다.

## 정책

| 정책                   | 프록시를 통과하는 트래픽                                                                                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 트래픽을 분할하지 않음 | 모든 트래픽                                                                                                                                                            |
| 중국 사이트 외 프록시  | 중국 도메인과 주소(`geosite:cn`, `geoip:cn`), 사설 주소를 제외한 모든 트래픽. 중국 관련 규칙과 일치하더라도 중국 외 사이트, Google, 홍콩과 마카오 주소에는 프록시 적용 |
| GFWList만 프록시       | GFWList의 도메인(Loyalsoldier 파일의 `gfw`, `greatfire`)과 Telegram 주소 범위. 먼저 **GFWList 업데이트**를 실행해야 하며, 파일이 없으면 이 모드는 거부됨               |
| 규칙 포트와 동일       | RoutingA를 포함한 규칙 포트의 모드                                                                                                                                     |

## 구현 방식

| 구현 방식     | 플랫폼                                                          | 참고                                                                                                 |
| ------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `redirect`    | Linux                                                           | iptables/nftables `REDIRECT`. TCP만 지원하며, **서비스 및 가로채기** 모드에서는 포트 53의 DNS도 코어의 DNS 모듈(포트 52353)로 리디렉션 |
| `tproxy`      | Linux                                                           | iptables/nftables `TPROXY`. TCP와 UDP 지원                                                           |
| `tun`         | Linux, Windows, macOS                                           | 코어가 TUN 장치를 엽니다. TCP와 UDP 지원. v2rayA와 코어를 자동으로 제외                                  |
| 시스템 프록시 | Windows. Linux와 macOS에서는 root 권한 없이 실행할 때(`--lite`) | 데스크톱의 프록시 설정을 변경(Linux에서는 GNOME과 KDE). 해당 설정을 따르는 애플리케이션에만 적용     |

`redirect`와 `tproxy`에는 root 권한과 `iptables` 또는 `nftables`가 필요합니다. `tun`에는 Linux에서 `/dev/net/tun`과 `ip`가, Windows와 macOS에서 관리자 권한이 필요합니다.

**제외할 인터페이스 접두사**는 지정한 인터페이스(Docker 브리지, VPN 터널. 기본값은 `docker*`, `veth*`, `wg*`, `ppp*`)로 들어오는 트래픽이 `redirect`와 `tproxy`를 거치지 않게 합니다. 해당 트래픽의 DNS는 **서비스 및 가로채기** 모드에서 가로채집니다.

`--redirect-respect-bound-device`(Linux)는 `SO_BINDTODEVICE`로 인터페이스에 바인딩된 TCP 연결이 `redirect`를 거치지 않게 합니다. NetworkManager의 연결 확인이 이런 연결이며, 리디렉션되면 연결이 제한됨으로 보고되어 이에 의존하는 앱이 계속 오프라인 상태가 됩니다. 기본값은 꺼짐입니다. 켜면 서비스가 cgroup BPF로 이런 소켓에 `0x80` 마크를 붙이는데, 커널 5.14 이상과 cgroup v2가 필요하며 없으면 `redirect`가 시작되지 않습니다.

## TUN

코어가 TUN 장치를 생성하고 주소를 할당합니다. **자동 라우트**를 켜면 v2rayA가 라우팅 경로를 설정하고, **서비스 및 가로채기** 모드에서는 시스템 리졸버가 코어를 사용하도록 설정합니다. 끄면 **라우트 스크립트 구성**의 설정 및 해제 스크립트가 이 작업을 수행합니다.

코어 자체의 연결, `direct` 아웃바운드, DNS 모듈의 업스트림 질의는 TUN에 들어가지 않습니다(Linux에서는 소켓 마크를 사용하고, Windows와 macOS에서는 물리 인터페이스에 바인딩). v2rayA와 코어는 항상 제외됩니다. **TUN 제외 프로세스**에 실행 파일 이름을 한 줄에 하나씩 입력하면 소유 프로세스를 식별할 수 있는 연결을 추가로 제외합니다. **서비스 및 가로채기** 모드에서 해당 프로세스의 DNS는 여전히 코어의 DNS 모듈로 전달됩니다. 기본 라우트보다 구체적인 라우트(직접 연결된 네트워크, 정적 라우트)도 TUN을 우회합니다.

**서비스 및 가로채기** 모드에서는 TUN에 도달한 포트 53의 암호화되지 않은 DNS에 코어의 DNS 모듈이 DNS 규칙에 따라 응답합니다. 암호화된 DNS는 가로채지 않습니다. 이때 Windows에서는 시스템 리졸버가 TUN 게이트웨이를 사용하도록 설정하고, macOS에서는 `127.0.0.1`의 코어 리스너를 사용하도록 설정하므로 포트 53이 비어 있어야 합니다.

나머지 두 모드에서는 TUN이 그런 릴레이를 만들지 않고 두 플랫폼 모두 시스템 리졸버를 변경하지 않습니다. 그래도 도착한 질의는 장치에서 직접 나갑니다. **자동 라우트**를 꺼서 라우팅 스크립트에 네트워크 구성을 맡긴 경우도 마찬가지입니다. v2rayA가 리졸버 설정을 바꾸지 않으므로 DNS 역시 스크립트의 몫입니다.

알려진 제한 사항: Windows와 macOS에서 LAN 리졸버에 직접 질의하는 애플리케이션은 여전히 TUN을 우회합니다.

## DNS

**설정 → DNS 설정**에는 DNS 모드와 코어의 DNS 모듈이 따르는 규칙이 있습니다.

| 모드                  | DNS 모듈 | 시스템 질의                                                       |
| --------------------- | -------- | ----------------------------------------------------------------- |
| 끄기                  | 실행 안 함 | 변경 없음                                                         |
| 서비스만              | 실행     | 변경 없음: 시스템 리졸버, 방화벽의 DNS 규칙, TUN 릴레이 모두 그대로 |
| 서비스 및 가로채기    | 실행     | 모듈로 전달됨: 리졸버가 바뀌고 포트 53이 리디렉션됨                |

모드는 원래 섞여 있던 두 가지 질문을 함께 답합니다. 모듈이 실행되는가, 그리고 시스템 질의가 모듈로 전달되는가입니다. **서비스만**은 두 질문에 서로 다르게 답합니다. **끄기**와 **서비스만**은 모두 `redirect`, `tproxy`, 시스템 프록시에서 53번 포트의 평문 TCP/UDP를 통과시키고, `tun`에서는 직접 내보냅니다. 암호화된 DNS는 원래 모듈로 전달되지 않으므로 그 때문에 가로채기를 포기할 필요가 없습니다. 다른 프로그램이 이미 DNS를 v2rayA로 보내고 있으면 **서비스만**을, DNS를 아예 대신 답해 줄 프로그램이 없어야 하면 **끄기**를 선택하세요.

규칙은 어떤 업스트림이 어떤 도메인에 응답할지, 질의를 직접 보낼지 지정합니다. 기본값은 내부 도메인 이름에 대한 DNS 질의를 `127.0.0.1:53`으로 보내고(`localhost`, 해당 주소에서 수신하는 리졸버 필요), `geosite:cn`은 `223.5.5.5`로 직접 보내며, 나머지는 프록시를 통해 `1.0.0.1`로 보냅니다. 아웃바운드가 `direct`이면 직접 질의합니다. 다른 값이면 로컬 SOCKS 인바운드를 통해 질의를 보내므로 SOCKS 트래픽과 같은 방식으로 라우팅됩니다. 도메인 목록이 비어 있는 규칙은 다른 규칙에서 지정하지 않은 모든 도메인에 응답합니다. 업스트림에는 주소(`8.8.8.8`, `dns.google`), `tcp://host`, DNS over TLS용 `tls://host`, DNS over HTTPS용 `https://host/dns-query`를 사용할 수 있습니다. DNS over QUIC는 지원하지 않으며 저장 시 거부됩니다.

**끄기**는 규칙을 숨기지만 지우지는 않습니다. 어차피 읽는 프로그램이 없고, 지우면 모드를 다시 켤 때 다른 구성이 적용되기 때문입니다.

저장은 규칙과 모드를 두 개의 요청으로 쓰며, 대화상자는 서비스가 어느 쪽을 받아들였는지 알려줍니다. 규칙은 저장됐지만 모드가 거부되면 그 사실을 그대로 알리고, 다시 시도할 때는 아직 빠진 것만 보냅니다.

DNS 설정 옆의 **노드 이름 확인 DNS**는 프록시 노드 서버 이름에 사용할 전역 확인자를 선택합니다. 서비스만 및 서비스 및 가로채기 모드에서 새 노드 연결과 TCP/HTTP 지연 시간 테스트에 적용되며 가로채기 여부와는 무관합니다. 끄기 모드는 모듈을 중지하고 노드에 기존 시스템 이름 확인 경로를 사용합니다. 이 모드에서는 노드 DNS 목록과 새로고침 버튼이 비활성화되지만 선택은 유지됩니다. 활성화된 모드를 저장하면 다시 사용할 수 있습니다. IP 노드는 DNS 질의가 필요 없습니다. 웹사이트, 구독 서버, DNS 업스트림 부트스트랩은 기존 방식을 사용합니다.

이 활성화된 모드에서 노드 연결과 TCP/HTTP 지연 시간 테스트는 내장 DNS 모듈이 질의를 처리할 준비가 될 때까지 기다린 다음 로컬 리스너에 질의합니다. 모듈은 선택한 업스트림에 직접 질의하거나 캐시 결과를 반환하며, 노드 이름 확인에 시스템 확인자를 사용하지 않습니다. 시작 시간 초과, 취소 또는 코어 종료 시 이름 확인을 중단합니다. 업스트림 실패는 DNS 질의 오류로 표시하며 다른 확인자로 전환하지 않습니다. 코어가 중지된 경우 지연 시간 테스트는 선택한 DNS 설정으로 임시 코어를 시작하고 테스트 후 종료합니다.

목록에는 DNS 규칙, 원래 시스템 설정, 내장 대체 목록의 IP 기반 UDP, TCP, DoT, DoH 엔드포인트가 표시됩니다. Linux에서는 `/etc/resolv.conf`에서 시스템 DNS를 읽고, DNS 하이재킹 중에는 원본 백업에서 읽습니다. 분류는 출처입니다: **직접 연결 그룹**, **로컬 DNS**, **프록시 그룹**, **대체 DNS**. 프록시 그룹을 선택해도 노드 DNS 질의는 항상 직접 전송됩니다. DoT/DoH 인증서를 검증합니다. 유효한 출처라는 뜻이며 네트워크 도달 가능성을 검사한 것은 아닙니다.

**자동**은 중복 출처를 제거한 뒤 직접 연결 → 로컬 → 대체 순서에서 첫 번째 비어 있지 않은 그룹의 첫 엔드포인트를 선택합니다. 명시적으로 선택한 엔드포인트와 마찬가지로 프로토콜과 포트를 포함한 전체 URL을 표시합니다. 예: `udp://223.5.5.5:53 (자동)`. 질의 실패는 DNS 오류로 보고하며 다른 엔드포인트로 전환하지 않습니다. 새로고침과 설정 또는 DNS 규칙 저장 시 목록을 다시 읽습니다. 저장된 출처가 사라지면 폼 값을 유지하며 경고합니다. 출처를 무효화하는 변경은 거부되므로 먼저 다른 엔드포인트나 자동을 선택하세요. DNS 캐시와 프리페치는 유지되며, 새 결과는 이후 연결에 반영되고 기존 연결은 현재 IP를 유지합니다.

## LAN 공유

**포트 공유**를 켜면 SOCKS, HTTP, 사용자 지정 인바운드가 `127.0.0.1` 대신 모든 인터페이스에서 수신하므로 다른 장치가 이 컴퓨터를 프록시로 사용할 수 있습니다. API 포트는 계속 루프백에서 수신합니다. 다른 장치의 트래픽에도 투명 프록시를 적용하려면 `redirect`, `tproxy` 또는 `tun`을 사용하고, **IP 포워딩**을 켜고, 트래픽이 들어오는 인터페이스가 제외 접두사에 포함되지 않게 한 다음, 해당 장치의 기본 게이트웨이를 이 컴퓨터로 지정하세요. 시스템 프록시 모드에서는 이 기능을 사용할 수 없습니다.
